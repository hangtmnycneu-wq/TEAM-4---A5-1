## Findings

### 1. TinyA5/1 demo cannot import the core
`demos_bap/demo_tinya51.py` imports `from core.tiny_a51 import TinyA51`, but the repository contains `core_bap/tiny_a5` (without `.py`) and no `core/tiny_a51.py`. The demo exits with `ModuleNotFoundError`.

### 2. Demo calls an API that TinyA51 does not implement
The demo calls `cipher.process_bits(P_slide)`, but the current TinyA51 class only exposes `generate_bit`, `generate_keystream`, and `encrypt_decrypt`. This causes `AttributeError` once the import is fixed.

### 3. TinyA5/1 output does not match the result claimed in the demo comments
For key `10010101001110100110000` and plaintext `111`, the current core returns:
- Keystream: `100`
- Ciphertext: `011`

The demo comments claim ciphertext `100` (and label it D), which would require keystream `011`. Confirm the intended register timing/bit order and the instructor's slide example, then update the core or the expected example consistently.

### 4. A5/1 standard test vector passes
The A5/1 implementation matches the pedagogical reference vector for key bytes `1223456789ABCDEF`, COUNT/frame `0x134`, and A-to-B stream `534EAA582FE8151AB6E1855A728C00` (114 meaningful bits; remaining six bits are padding). The test passes after converting each key byte to LSB-first bit order, consistent with the reference convention.

This passing vector is stronger evidence than round-trip tests alone, but the team should still document the exact key/frame bit-order convention in README.
